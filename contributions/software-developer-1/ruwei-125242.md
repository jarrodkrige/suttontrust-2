FirstGen Website — Developer‑Focused Change Proposals
1. Information Architecture & Routing
1.1 “What Is FirstGen?” Definition Block (Homepage)
Requirement:

Add a prominent above‑the‑fold section with a concise definition and example criteria.
Include a CTA button: Am I FirstGen?.

Reason:
Clearly defining eligibility prevents users from self‑excluding due to uncertainty.

1.2 “Am I FirstGen?” Eligibility Flow
Requirement:

Implement a short, client‑side questionnaire (3–5 yes/no questions).
Display an inline result state (eligible / likely eligible / unsure → contact).
No login required.

Reason:
Quick self‑identification increases conversion and reduces bounce rate.

1.3 Sixth‑Form Dedicated Section
Requirement:

Create route: /sixth-formers.
Content focused only on pre‑18 support (avoid university‑only resources).
Link prominently from main nav.

Reason:
Separating audiences avoids cognitive overload and improves relevance.

2. User Flows & Conversion
2.1 Core Action Pathways
Requirement:
Implement three clearly defined CTAs across the site:

Get Mentoring
Join an Event
Volunteer / Support Others

Each CTA maps to a separate landing page with scoped content.
Reason:
Clear task‑oriented flows reduce decision paralysis.

2.2 Mentor Matching Preview
Requirement:

Static explainer section describing matching criteria (subject, background, availability).
Optional mentor profile cards (first name, role, journey summary).
No personal data exposed.

Reason:
Transparency builds trust and reduces signup anxiety.

2.3 Low‑Commitment Engagement Options
Requirement:

Event types tagged as One‑off, 15‑minute, or Webinar.
Filterable list component for time commitment.

Reason:
Short commitments fit exam‑heavy sixth‑form schedules.

3. Content & Resources
3.1 UCAS Support Hub
Requirement:

Route: /resources/ucas.
Sections for:

Personal statement structure
Super‑curricular examples
FirstGen‑specific pitfalls


Content editable via CMS.

Reason:
UCAS support is the highest‑value need for this audience.

3.2 Student Stories Module
Requirement:

Lightweight testimonial system (text or short video embeds).
Metadata: GCSE/A‑Level subjects, target degree, outcome.

Reason:
Peer representation reduces imposter syndrome.

4. Forms & UX
4.1 Mobile‑First Form Design
Requirement:

Forms must be usable one‑handed on <375px screens.
Maximum 5 required fields per step.
Progress indicator on multi‑step forms.

Reason:
Sixth‑formers primarily access sites via mobile devices.

4.2 Progressive Disclosure
Requirement:

Collect minimal data initially (name, email, year group).
Defer sensitive details until trust is established.

Reason:
Lower friction increases initial sign‑ups.

5. Safeguarding & Trust
5.1 Safeguarding & Data Transparency Page
Requirement:

Route: /safeguarding.
Clear sections on:

Under‑18 policies
Data storage and contact rules
Parental awareness stance


Linked from footer and forms.

Reason:
Safeguarding clarity is essential for schools, parents, and students.

5.2 Trust Signals
Requirement:

Display partner logos (schools, universities, funders).
Use alt text and accessible captions.

Reason:
Social proof increases legitimacy for first‑time visitors.

6. Accessibility & Compliance
6.1 WCAG 2.1 AA Baseline
Requirement:

Semantic HTML
Keyboard navigability
Sufficient colour contrast
Screen‑reader compatible forms

Reason:
Accessibility ensures inclusion of neurodiverse and disabled students.

Requirement:

All text content (definitions, testimonials, resources) editable without code deployment.

Reason:
Allows non‑technical staff to keep content current and relevant.

7.2 Analytics Hooks
Requirement:

Track:

CTA clicks
Eligibility flow completion
Form drop‑off points



Reason:
